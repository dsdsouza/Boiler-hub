# Guided onboarding

`/onboarding` replaces the old “Light your boiler” setup page. It is public until the account step; all data mutations still require a verified Supabase user.

The journey asks for identity, name, goal and starting point, introduces Pip, and returns from Google OAuth to the same account step. Every goal then uses one **Pip** extension for calendar-link finding, laptop reminders and focus blocking. Setup continues with a calendar reading, status, optional extra sources and team joining, a recommendation, and completion. Students also connect coursework and review the imported deadlines. A deadlines path adds an optional first task and, when a task is entered, an optional target date. Team goals finish in Teams; other paths finish in My Boiler.

Only Continue unlocks the next question. Required answers must be valid. Back, the progress controls, vertical scrolling and swiping revisit unlocked steps. Previously unlocked forms stay mounted so unsent source fields survive back navigation. Pip installation, student coursework import and deadline review can be deferred through an explicit confirmation dialog. A deferred coursework import omits the review step and is recorded separately from a verified import. Teachers and team leads keep the installation and calendar options, can skip them, and do not need a personal first task to finish; other non-student roles can skip adding a feed and are not asked to add courses. **Finish later** saves an unfinished draft and leaves the journey without claiming setup is complete.

The page extends the incumbent [iron-and-brass design reference](./design/README.md), using the existing Bebas Neue display type, Inter body text, Pip artwork, shared controls and color tokens. The new gates do not establish a separate visual system.

## Saved progress

- Tab-local answers use `sessionStorage["boiler:onboarding:v1"]`, including the current step. The storage key remains stable, while the draft format is version 2. The sign-in action checks that storage works before leaving.
- After login, `GET /api/me/onboarding` loads the verified user’s saved draft. Drafts are bound to that user; another account’s draft is discarded.
- After the verified account is loaded, the earlier anonymous answers save immediately through `PATCH /api/me/onboarding` into that user’s Supabase `user_metadata.onboarding`, without needing Continue. Later edits autosave after a 400 ms pause. Continue, Finish later and final completion use the same ordered writer, so an earlier background request cannot overwrite newer progress. No database migration is needed.
- The server verifies the caller through the ordinary user client, then updates only that caller's parsed onboarding metadata through the existing server-only admin client. No caller-supplied user ID, auth settings or app metadata reaches the admin writer. This avoids consuming the public Auth `/user` sign-in rate bucket for every autosave; that bucket is shared by clients behind a server IP. No new credentials or Auth settings are needed. See [Supabase rate limits](https://supabase.com/docs/guides/auth/rate-limits) and [server metadata updates](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid).
- Upstream throttling stays a `429` with a retry hint rather than becoming a server error or a false signed-out response. Autosave respects the retry window, preserves the newest local answers, and suppresses queued writes and immediate retries during the cooldown.
- Signed-in edits back up the verified owner's draft during the input event itself. Leaving before the network debounce does not depend on the browser delivering `pagehide` or its keepalive request; reopening can recover the latest answer.
- The progress label reports **Saving answers…**, **All changes saved**, or **Answers not saved yet**. A failed background save offers **Retry saving** and retries when connectivity returns. “Saved” means the account accepted the current answers, not merely that a request started. Autosaving answers never marks a question or setup complete.
- Pending answers also have an owner-specific browser backup, read only after that owner is verified. It can recover a failed save after closing the tab. An acknowledged write removes only its matching backup, preserving any newer edits. Hiding or leaving the page attempts to flush pending edits with keepalive requests; delivery still depends on the browser and network, so a fresh tab can recover a dropped final write from the backup. Browser backups are best effort when site storage is blocked.
- Writes carry the expected authenticated owner. If the account changes between loading a draft and sending a request, the server rejects the write rather than applying the previous person’s answers to the new account. Anonymous drafts remain tab-local until sign-in.
- If the initial saved-draft read fails, the page offers **Try loading again** and keeps the forms and **Finish later** unavailable. It cannot overwrite saved answers with the initial empty draft. Finish later saves `finished: false`; a failed save keeps the user on the page with an error.
- Version 1 drafts retain their answers but clear completion of the previously skippable setup gates, recommendation and ready step. A previously finished draft reopens at the Pip gate when appropriate and must pass the current checks.
- Completion saves the profile name and status. An optional first task uses a stable, owner-scoped UUID, so retries update the same task. The deadline is sent as the user’s local end-of-day timestamp.
- Tokens and subscription URLs never enter the onboarding draft or setup metadata. Existing source forms handle them. Calendar handoffs use the existing ten-minute, tab-scoped helper storage and strip the fragment from the address bar.

## Extension detection

Onboarding checks the Focus with Pip extension, currently **v0.3.3**, for every goal. Its isolated content script runs only on the allowed Boilerplate production origins and local development origins. The page sends `bp-extension:ping` with extension kind `focus` and a fresh nonce. Pip returns `bp-extension:pong`, the nonce, and its manifest version. The page checks message origin, source, kind and nonce, and requires a valid version at least **0.3.2**. An older version shows update instructions.

Continue stays disabled until the current Pip extension answers. The check repeats when the tab regains focus, and users can select **Check again**. A download alone does not confirm installation. Newly installed extensions may require refreshing the onboarding page; answers are retained. Updating an unpacked installation requires replacing its files, reloading Pip in Extensions, then refreshing Boilerplate.

This is ordinary browser installation detection, not tamper-proof attestation or an authorization boundary. Completion also rejects a missing or unsupported extension version, but it does not cryptographically prove that the extension is installed.

Pip’s **Use in onboarding** action opens the paired, trusted Boilerplate origin at `/onboarding#feed=…`. The selected feed is ready for explicit review and connection in the calendar step. **Review import in Boilerplate** still opens `/calendar-helper` for the independent import workflow. The separate Calendar Finder remains available outside onboarding; it is not a second required install. See [calendar import helpers](./browser-helper.md).

Rebuild Pip with `pnpm pip:package` after editing `focus-extension/`. The download is `public/downloads/boilerplate-focus-extension.zip`. The package reuses the canonical scanner and protocol from `browser-helper/`, and its tests check archive/source equality. Rebuild the separate Calendar Finder with `pnpm helper:package` after editing its sources.

## Coursework and deadline review

For a student who chooses to complete coursework setup, Google Calendar alone does not verify a course import. There must be at least one connected ICS source with **Coursework** enabled. Every connected coursework ICS source must have status `ok` and a successful sync timestamp. A failed coursework source keeps the gate closed even when another one works. Sources can be connected through Pip’s handoff or by pasting a feed into the existing form.

`POST /api/me/onboarding/check` requires the signed-in user and refreshes sources server-side with `freshSources: true`. A healthy coursework result returns the current boiler reading and an encrypted review receipt. The next step lists imported coursework deadlines, course names and supplied due dates. Continue verifies the import only after the user’s explicit review checkbox; Skip opens a confirmation to defer coursework setup instead. A readable feed with no deadlines can pass only after the user explicitly confirms that empty result against the school calendar; it does not imply the school has no work due. Refreshing or adding a source clears the checkbox and receipt so the result must be reviewed again.

The receipt expires after two hours and binds the authenticated owner to a digest of the reviewed coursework source identities/labels, deadlines and events. It carries the owner, purpose, digest and issue time, with no source URLs, feed credentials or event contents. It stays in page memory rather than the saved draft. At completion, students who have not deferred coursework setup have their sources refreshed again, and the server verifies the receipt and explicit review flag. Explicitly deferred setup does not claim an imported source or deadline-review timestamp. Changed imported contents, removed sources, failing sources, another owner, an expired receipt or an invalid receipt require another check and review.

Completion metadata records the setup version, extension version, explicit extension/coursework deferrals, check time, coursework source IDs and review time. Source URLs and event contents are not copied into it. The receipt’s digest is used for verification rather than storing a second copy of imported calendar data in onboarding metadata.

## Verification

Use `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm build` to check the source. Private browser states and test captures stay outside the committed source.

The onboarding model tests cover adaptive paths, unlocking and migration of legacy drafts. API and receipt tests cover ownership, unauthenticated requests, partial autosaves without completion side effects, account changes, supported Pip versions, fresh coursework checks, changed/failed/removed sources, receipt expiry, empty readable feeds, retry-safe first-task writes, status saves and save failures. Backup tests cover owner separation, storage failures and newer edits surviving an older acknowledgment. Browser fixtures cover immediate sign-in handoff saves, editing without Continue, ordered slow saves, retries, closed-tab recovery, account switching, anonymous answers, mobile layouts, navigation, draft restoration, missing and installed-extension responses, explicit deadline review, calendar errors, retained source forms and final navigation. Fixture responses are not evidence of a native extension installation or a live school import.

Real Google OAuth was verified against the existing Supabase project on October 24, 2026: the saved public answers returned to the account step, Calendar connected, final profile/status and a dated first task persisted, and the flow opened My Boiler. Temporary profile changes, onboarding metadata and the QA task were restored afterward. Google’s unverified-app warning and consent were completed by the account owner. This earlier OAuth check does not establish a live Brightspace import through the current coursework gates.

Local development needs `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Full calendar sync also needs the existing server credentials in `.env.example`; keep those server-side. Supabase currently permits `http://localhost:3000/auth/callback` (also ports 3001 and 3002), so use an allowed origin for OAuth. A preview on an unlisted port falls back to the Supabase site URL and cannot complete the local PKCE journey. Authentication derives the callback from the browser origin, safely preserves the next path, and returns failures to the saved onboarding flow.

The local workflow suite checks completion across Chromium, Firefox, WebKit and a phone, including a revised deadline and restored draft. Live workflow tests use synthetic accounts and restore their original profile and metadata. The Google consent path is verified separately with a real account; it is never simulated and described as a real Google login. A native Brave check on October 24, 2026 verified Pip v0.3.3 detection, subscription scanning and the Use in onboarding handoff, a real Brightspace coursework import, four title/course/due-time samples against the school calendar, the unchecked deadline-review gate, server-validated completion, and Finish later resumption. The test reused an existing signed-in school account and did not change school assignments or enable new feeds. Feed credentials and coursework contents are excluded from repository evidence. No universal school compatibility claim is made.
